Patterns & Gotchas

A field guide to the things that bite you. These are the recurring lessons behind a stable DPB2 bot, read them before you spend hours debugging the same issue.

Coroutine discipline

The DPB coroutine scheduler only permits certain awaits. Violations throw CoroutineBehaviorException and kill the loop.

Don'tDo
await someTask (raw external Task)await Coroutine.ExternalTask(someTask)
await Task.Yield()await Coroutine.Sleep(0)
await ExilePather.ReloadAsync(...)ExilePather.Reload(true) (synchronous)

Inside a coroutine you may only await Coroutine.Sleep/Yield, framework coroutine methods (TaskManager.Run, Coroutines.InteractWith), or Coroutine.ExternalTask.

Reload the pathfinder per area

Before any pathing or explorer use in a freshly-entered area, reload the pather once, guarded on the area hash, and gate everything else on IsReady:

if (LokiPoe.LocalData.AreaHash != _pathHash)
{
    ExilePather.Reload(true);     // synchronous, never await the async variant
    ExilePather.ClearObstacles(); // dynamic obstacles are per-map
    Explorer.Reset();
    _pathHash = LokiPoe.LocalData.AreaHash;
}
if (!ExilePather.IsReady) return;  // gate explorer.Tick()/FindPath behind this

Skip it and you get "Cannot use PathExistsBetween before Reload is called."

Enable the input hook once

Call LokiPoe.ProcessHookManager.Enable() a single time in Start(). Without it, UseAt/UseOn return ProcessHookManagerNotEnabled. Calling it every loop inflates the main loop to ~800–1000 ms; once-only keeps it ~200 ms and the bot stays responsive.

Held-fire / channeling

For continuous fire, use BeginUseAt(slot, inPlace, pos, clearKeys: false) and never call ClearAllKeyStates() between shots, any clear stops the held key and breaks channeling. Only clear key states immediately before a dodge, so the roll registers; then resume firing.

Some values are stale or static

Metadata existence ≠ a live value

A member appearing in the DLL doesn't mean it tracks live state. Known traps:

  • InstanceInfo.MonstersRemaining counts inactive statue-monsters, it never reaches a low value, so don't gate map completion on it alone.
  • Crossbow ammo (Skill.UsesAvailable, bolt stats, CurrentSouls) is static/stale, it doesn't follow the live magazine.
  • Skill.CanUse/CanUseEx grayed-out detection flip-flopped across versions (added 0.4.5.19 → reverted 0.4.5.20 → re-added 0.4.5.21). Check your build before relying on it.

Guard every entity/item read

Property reads can throw. Item.Name/Class/Rarity throw "BaseItemType not found" for some ground items; HasVisibleHighlightLabel can throw NullReferenceException. An unguarded read inside a LINQ filter crashes the whole task.

static bool SafeShouldLoot(WorldItem w)
{
    try { return /* read w.Item.Rarity / Class / Metadata */ ...; }
    catch { return true; } // never silently skip a possible jackpot
}

Prefer matching on Metadata (language-agnostic, less throw-prone) over localized Name for detection logic.

Task ordering

Because the TaskManager restarts evaluation whenever a task returns true, list order is your priority system. A robust endgame order:

Death → Flask → Evade → Watchdog → Telegraph-dodge →
Precursor → Loot → Combat → Boss → Chest → Shrine →
Mechanics → Explore → MapEnd
Loot before combat (with a close-threat gate)

If combat runs first, any monster in range keeps the combat task returning true and loot never gets a turn, drops pile up unlooted. Put loot before combat, but give the loot task a close-threat gate: if a hostile is within engage range and the item isn't already adjacent, return false so combat clears the pack first. You get "fight pack → loot its drops → move on."

Per-visit flags & the area hash

Update the area hash before any early-return

In a task that uses a per-visit "done" flag (e.g. a stash task that should run each hideout visit), put the area-hash reset before any if (!IsHideout) return false. If the reset sits after the early-return, the hash freezes while you're in maps and the same hideout never counts as a new visit, the flag sticks true forever. Let in-map ticks update the hash to the map's value so the next return registers as a change.

Town portals are MultiplexPortal

The town/return portal you create with B in a map is a MultiplexPortal NetworkObject, not the Portal type, so GetObjectsByType<Portal>() misses it. Find return/map portals by matching both:

bool IsPortal(NetworkObject o) =>
    o is Portal
    || o.Name.Contains("Portal")
    || o.Metadata.Contains("MultiplexPortal");

When opening the next map, exclude completed portals (their name contains "Complet"/"Conclu") so you don't re-enter a finished map.

Anti-stuck & recovery

Optimal routing is solved (ExilePather gives the best navmesh route). Getting stuck is a movement-execution problem. Defensive measures that keep a bot progressing:

  • String-pull, aim at the farthest path waypoint with clear line-of-sight (CanObjectSee) so you never cut a corner into a wall.
  • Give-up counters, after N consecutive no-progress events, abandon the target: Explorer.Ignore(loc) for explore, blacklist the object id for loot/chests.
  • Dynamic obstacles, when a corridor is navmesh-walkable but physically blocked, AddCircleObstacle ahead + SignalObstacleUpdate() so future paths route around it. Clear obstacles on area change.
  • Blind dodge off-mesh, after a resurrect that lands you off the navmesh, FindWalkableNudge finds nothing; dodge-roll blindly toward the map entry point (guaranteed on-mesh) to get back onto the navmesh.
  • Activity guard, don't treat "standing still while a nearby enemy is losing HP" as stuck; ranged standing combat is legitimate.

Detecting a full inventory

Per-item-id counters don't work for "can't pick up"

Coroutines.InteractWith returns OK even when an item can't be picked up (inventory full), so a naive loop re-targets it forever. A per-item-id attempt counter fails too: each re-detection gets a different WorldItem id, resetting the count. The working signal is the inventory item count: snapshot Items.Count before/after interacting; if a non-stackable item's count didn't grow, it didn't fit. After a few such failures, go dump/sell. (Skip stackables; they merge without growing the count.)

Combat changes are regression-prone

"Smart" combat additions (telegraph dodging, line-of-sight gating, door filters) frequently regress working behaviour. For example, a too-eager telegraph dodge makes the bot endlessly sidestep instead of closing in to attack a ranged enemy. Be conservative:

  • Only telegraph-dodge for boss/unique threats, and only when they're genuinely close.
  • Keep shooting as the default behaviour; treat kiting/dodging as occasional support, not the main loop.
  • When surrounded and healthy, an AoE build should nuke in place, not flee into a wall.
  • Test each combat tweak in isolation; they interact in surprising ways.

Map completion logic

IsMapCompleted is reliable when true, but can stay false at 100% explored if the objective (often the boss) isn't done. A robust "map done" signal combines both:

bool mapDone = LokiPoe.InstanceInfo.IsMapCompleted
    || (!explorer.HasLocation && explorer.PercentComplete >= 80);

If you must kill the boss but it never loaded (the explorer marked tiles "seen" by line-of-sight without physically entering the arena), re-sweep: tighten the explorer's seen/known radius and Explorer.Reset() to force physical traversal, up to a sweep cap.

Pre-flight checklist

Before you blame the API
  • Did you ProcessHookManager.Enable() in Start()?
  • Did you ExilePather.Reload(true) for this area, and gate on IsReady?
  • Are all item/entity reads wrapped in try/catch?
  • Is every await a framework coroutine or wrapped in ExternalTask?
  • Is Tick() free of actions (flags/reads only)?
  • Does at least one task always make progress so the loop never idles in a map?
