Core Concepts

Plugin Architecture

The interfaces DPB2 looks for, how it composes them, the lifecycle each one follows, and the all-important Tick() contract.

Everything is an IBase

DPB2 discovers plugins by scanning your DLLs for concrete types that implement IBase. Every loadable component, bots, routines, movers, plugins, content, ultimately derives from it. IBase provides the two fundamental lifecycle calls:

public interface IBase
{
    void Initialize();    // called once when the component is loaded
    void Deinitialize();  // called once when it is unloaded
}

Most components also implement IAuthored (Name / Author / Description / Version) and IEnableable (Enable / Disable), plus a Tick() method discussed below.

Component types

There is no built-in IBot, IRoutine or IPlayerMover shipped inside the core DLL, you (or a community plugin) provide them. Each plays a distinct role:

Anatomy of an IPlugin

IPlugin is a composite of several small interfaces. Implementing it means satisfying all of them:

IPlugin = IConfigurable + IMessageHandler + IAuthored + IBase + IEnableable + ILogicProvider
  • IConfigurable, exposes UserControl Control (a WPF settings panel) and JsonSettings Settings.
  • IMessageHandler, MessageResult Message(Message message) for the event/message bus.
  • IAuthored, Name, Author, Description, Version.
  • IBase, Initialize() / Deinitialize().
  • IEnableable, Enable() / Disable().
  • ILogicProvider, Task<LogicResult> Logic(Logic logic).
A plugin's Logic() is not auto-pumped

The PluginManager has Start/Stop/Tick/Enable/Disable but no obvious Logic pump, a plain plugin's Logic() may not be called for you. Drive plugin behaviour from its UI, from Message(), or have a bot/task call into it. For self-contained background work, do it from Tick() (flags only) plus a coroutine you own.

Lifecycle

For an enabled IPlugin, the order of calls is:

Initialize()  →  Enable()  →  Tick() … Tick() … (every ~30 ms)  →  Disable()  →  Deinitialize()
  • Initialize, one-time setup. A common pattern is to assign a static Instance here so your WPF UI can call back into the plugin.
  • Enable / Disable, toggled when the user enables the component or stops the bot. Acquire/release runtime resources here.
  • Tick, the high-frequency heartbeat (see below).
  • Deinitialize, final teardown on unload.

The Tick() rule

The TaskManager ticks at roughly 30 ms and propagates Tick() to every component. So every IBot / IPlugin / IRoutine / IPlayerMover / IContent must implement public void Tick(), and it runs ~33 times a second.

Tick() is for control logic only, never actions

Use Tick() to set flags, collect object info and do calculations (reading a hotkey is borderline-OK). Do not press keys, click, interact or move in Tick(). All actions belong in the coroutine / Run() / Logic() flow.

The idiomatic split:

  • ITask and IPlayerMover Tick() bodies usually stay empty.
  • The IBot's Tick() may read a hotkey and set a flag, then pump its own main coroutine, where the real actions run.
// Reading a pause hotkey in the IBot's Tick() is compliant:
// GetAsyncKeyState reads the physical key regardless of window focus,
// it only SETS a flag here, the action happens elsewhere.
public void Tick()
{
    if ((GetAsyncKeyState(Keys.B) & 0x8000) != 0 && AltHeld())
        TogglePause();   // just flips a bool
}
Pause done right

A robust pause toggles LokiPoe.ProcessHookManager.Disable() on pause (bot stops injecting input → full manual control) and Enable() on resume. Because GetAsyncKeyState reads physical keys independent of the hook, your resume hotkey still works even while injection is disabled.

Settings & UI

Persisted settings use JsonSettings. The canonical pattern is a singleton settings class bound to a WPF UserControl via DataContext, with a static Instance set in Initialize() so the UI can call back into the plugin.

public sealed class MyPluginSettings : JsonSettings
{
    private static MyPluginSettings _instance;
    public static MyPluginSettings Instance =>
        _instance ?? (_instance = new MyPluginSettings());

    private MyPluginSettings() : base(GetSettingsFilePath(
        Configuration.Instance.Name, "MyPluginSettings.json")) { }

    private int _scanRadius = 60;
    public int ScanRadius
    {
        get => _scanRadius;
        set { _scanRadius = value; NotifyPropertyChanged(() => ScanRadius); }
    }
}

Bind it in XAML:

<UserControl ...
    DataContext="{x:Static local:MyPluginSettings.Instance}">
  <StackPanel>
    <TextBox Text="{Binding ScanRadius}" />
  </StackPanel>
</UserControl>
Some builds have no settings tab

On builds where the window exposes no settings tabs (only the Bot/Routine/Mover dropdowns, Render and Start), neither IBot.Control nor IPlugin.Control surfaces. Tune everything by editing the JSON directly at Settings\<config>\<Name>Settings.json with DPB closed, it loads settings on start and saves them on exit, so edits made while it runs are overwritten.

The message bus

DPB2 routes events through Message(). Messages are processed on the main coroutine thread, in a defined order: ContentManager.Contents → RoutineManager.Current → PlayerMoverManager.Current → PluginManager.EnabledPlugins. Keep Message() handlers cheap, do not run long calculations there. A typical use is reacting to an area changed message to reset per-area state.
