Core Concepts

The Bot Loop

An IBot is a thin shell around a TaskManager and a Coroutine. Tasks decide; the coroutine acts. This is the pattern almost every DPB2 bot uses.

The big picture

The BotManager runs a background BotThread and calls your bot's Tick() on an interval. Your bot holds two things:

  • A TaskManager, an ordered list of ITask units it evaluates each cycle.
  • A Coroutine, the async "main loop" where actions actually execute.

Both new TaskManager() and new Coroutine(Func<Task>) are public, so you construct them yourself.

Coroutine API surface

Coroutine.Sleep(ms), Coroutine.Yield() and Coroutine.Wait(...) are static. Resume(), Dispose() and IsFinished are instance members.

A minimal IBot skeleton

public class MyBot : IBot
{
    private readonly TaskManager _taskManager = new TaskManager();
    private Coroutine _coroutine;

    public void Initialize()
    {
        // order == evaluation order
        _taskManager.Add(new DeathTask());
        _taskManager.Add(new CombatTask());
        _taskManager.Add(new LootTask());
        _taskManager.Add(new ExploreTask());
    }

    public void Start()
    {
        // CRITICAL: input injection must be enabled or UseAt/UseOn return
        // ProcessHookManagerNotEnabled. Call this ONCE, not every loop.
        LokiPoe.ProcessHookManager.Enable();

        _taskManager.Start();
        _coroutine = new Coroutine(() => MainLoop());
    }

    public void Tick()
    {
        _taskManager.Tick();
        if (_coroutine == null || _coroutine.IsFinished)
            _coroutine = new Coroutine(() => MainLoop());
        _coroutine.Resume();
    }

    public void Stop()
    {
        _taskManager.Stop();
        try { _coroutine?.Dispose(); }
        catch (CoroutineStoppedException) { /* expected, swallow it */ }
    }

    private async Task MainLoop()
    {
        while (true)
        {
            if (!LokiPoe.IsInGame)
            {
                await Coroutine.Sleep(250);
            }
            else
            {
                var result = await _taskManager.Run(
                    TaskGroup.Enabled, RunBehavior.UntilHandled);

                if (result == RunTasksResult.NoTasksRan)
                    await Coroutine.Sleep(1000);
            }
            await Coroutine.Yield();
        }
    }
}

Disposing the coroutine cleanly

Coroutine.Dispose() unwinds the loop by injecting a CoroutineStoppedException at the current await. If you don't catch it, it leaks up to BotManager and is logged as an InjectionDesyncException on every Stop. Always wrap Dispose() in try/catch and ignore that exception.

ITask, the state-machine unit

An ITask is one decision unit. Its key method is Task<bool> Run():

  • Do one action and return true → the TaskManager restarts from the first task and re-evaluates everything.
  • return false → fall through to the next task in the list.

With RunBehavior.UntilHandled, tasks run in order until one returns true. ITask also requires the usual Start/Stop/Tick/Message/Logic plus the IAuthored members; these are mostly no-ops.

public class LootTask : ITask
{
    public async Task<bool> Run()
    {
        var item = NearestLootableItem();
        if (item == null)
            return false;                 // nothing to do, let the next task run

        await Coroutines.InteractWith(item, false);
        return true;                      // handled, restart evaluation from the top
    }

    public void Tick() { }                // empty, actions go in Run(), not Tick()
    // …Start/Stop/Message/Logic + Name/Author/Description/Version
}
Task order is your priority system

Because evaluation restarts from the top whenever a task returns true, the list order is the priority. A practical ordering is Death → Flask → Evade → Loot → Combat → Boss → Explore → MapEnd. Put survival first and map-completion last. See Patterns & Gotchas for why loot usually belongs before combat.

Coroutine rules you must respect

The DPB coroutine scheduler is strict about what you may await. Breaking these throws CoroutineBehaviorException and stops your loop.

Never await an external Task directly

Inside a coroutine you may only await Coroutine.Sleep/Yield, framework coroutine methods (like TaskManager.Run or Coroutines.InteractWith), or an external task wrapped in Coroutine.ExternalTask(theTask). Awaiting a raw Task (e.g. ExilePather.ReloadAsync) throws "No continuation was queued … external task was awaited."

Never use await Task.Yield() in a task

It throws the same external-task exception the moment it runs. Use await Coroutine.Sleep(0) instead.

Routines vs. multi-task bots

DPB2 supports a separate IRoutine component for combat, invoked through RoutineManager.Current.Logic("hook_combat"). This decouples combat from the bot so a single routine can serve many bots. The trade-off:

ApproachProsCons
Combat inside the task listMost responsive; full control; no hook indirection.Combat is coupled to that bot.
Combat as an IRoutinePluggable / reusable across bots.Extra indirection; per-build skill config needed.

Both are valid. Many PoE2 bots keep combat in the task list for responsiveness; others adopt a routine for extensibility. Choose based on whether you need swappable combat.

Don't let the loop idle in a map

No task should return false forever while in a map

If you ever reach a state where every task returns false while the character is in a map, the bot stands idle and can die. Always have a fallback task (explore, leave, or recover) that makes progress so the loop never stalls.
